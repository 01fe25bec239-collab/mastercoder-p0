# Normative V2.1 wire encoding

This is an architecture specification, not an implemented protocol. `REGISTRY.json` defines every contract's complete ordered fields and semantic conditions; each `*.schema.json` is its strict decoded JSON projection. P0-06 must independently implement and compare Rust and TypeScript. Existing V2 names identify refined contracts; V2 had no complete wire freeze. No existing deployed V2 wire compatibility is claimed.

## Exact bytes

Each record is a definite-length CBOR array `[type_name, 1, field_0, …, field_n]`, where type_name is the exact ASCII registered name and 1 is wire_revision. Field order is `x-cbor-order` and registry order. Nested records use the same representation. Integers and lengths use shortest RFC 8949 encoding. No maps, tags, floats, CBOR null/undefined, indefinite lengths, alternate integer encodings, trailing bytes or unregistered fields are allowed. Boolean is exactly CBOR false/true. Maximum record 16 MiB, nesting 32, array length 65,536 unless a narrower constraint applies. Reject oversized length before allocation.

Primitive `u16/u32/u64/i16/i64` means the stated mathematical width; encode unsigned positive values with major type 0, negatives with major type 1. `i64` timestamp fields are UTC microseconds since Unix epoch, except explicitly named `timestamp_seconds`; monotonic durations have explicit units. Database security decisions sample `clock_timestamp()` after locking and do not trust producer times. The human JSON projection uses canonical decimal strings for u64/i64 (including seconds) so TypeScript uses BigInt, never Number. Reject leading zero, plus sign, negative zero, exponent, overflow and numeric JSON values for these widths. u16/u32/i16 use JSON integers.

UUID is exactly 16 raw bytes (canonical lowercase hyphenated string in projection). Digests and bytes32 are exactly 32 bytes; bytes64 exactly 64; generic bytes and Git path are byte strings. Projection bytes are lowercase even-length hexadecimal. `authority_epoch` is a random UUID compared only for equality, not a counter. Repository epochs, credential generations and journal sequences are unsigned counters scoped as specified. GitOidV1 explicitly binds SHA1=0/20 bytes or SHA256=1/32 bytes; SHA256 provider cells remain disabled pending qualification.

Text is shortest valid UTF-8, Unicode NFC; reject non-NFC rather than transforming an authenticated value. Identifiers/origins/refs use the strict schema lexical grammar, no implicit case fold, slash fixup, percent decode or URL redirect. Origin is exact HTTPS origin, no path/userinfo/query/fragment; reject default `:443` spelling and invalid host labels. Git ref additionally rejects `..`, `@{`, backslash, repeated slash, final slash/dot, component starting dot or ending `.lock`; normalize nothing. Git paths are exact bytes, no Unicode normalization: reject NUL, absolute path, empty/dot/dot-dot components, slash suffix, backslash and case/Unicode collisions for the selected filesystem cell. Limits are byte limits in addition to JSON character limits. Credential keys use WebAuthn COSE ES256/P-256 and must be validated by the Approval Authority; encoded key bytes are opaque only to the general envelope parser.

A schema enum uses its **zero-based position in the registered enum array** encoded as an unsigned integer (semantic width u16); primitive provider/effect_kind enums follow the registry primitive arrays. An unknown enum code rejects. An ordered array preserves order. A set array is sorted lexicographically by the complete canonical encoded element bytes and contains no duplicate encoding. Named identity keys also must be unique (unit_id, path, tool_id, step_id); encoding uniqueness alone is insufficient. Optional values are ALWAYS present as a zero-length array for absent or a one-element array for present. Missing fields and null are rejected. An empty set is distinct from absent; nonempty requirements are semantic conditions.

## Digests and signatures

For any registered type T, `D(T,x) = SHA-256(UTF8("MASTERCODER/V2.1/" + T + "/sha256") || 0x00 || CBOR(x))`. No stored digest/signature field is included in its own payload. Hash referenced immutable payloads before dependents; all dependencies form a DAG. Plans reference custody_id; custody snapshots may reference plan_digest; immutable request/Effects records precede plan and runtime EffectIntent records. The mutable current pointer and runtime effect states never change a previously signed payload.

SignedEnvelopeV1 carries a detached Ed25519 signature. Define A as the fixed CBOR array `[contract_type, payload_digest_bytes, signer_uuid_bytes, key_uuid_bytes, credential_generation_uint]`. Sign exactly `UTF8("MASTERCODER/V2.1/signature") || 0x00 || CBOR(A)` using pure Ed25519 (not Ed25519ph). Verify the payload digest independently, then verify signature and signer role/key registration, tenant scope, repository epoch, current authority epoch and revocation. A valid key for another role cannot sign trusted evidence. Signature envelope is not recursively signed. Multi-authority journal receipts are separately signed JournalWitnessReceiptV1 objects naming one exact entry_digest, not an untyped list of arbitrary signatures.

WebAuthn authenticator signatures are a separate algorithm: verify ES256 over exact authenticatorData concatenated with SHA256(exact clientDataJSON), after validating expected challenge/type/origin/RP/UV and credential state. The challenge bytes are D(ApprovalChallengeV2,challenge), base64url without padding in clientDataJSON. `ceremony_digest` hashes WebAuthnCeremonyV1. The Approval Authority subsequently signs HumanApprovalAssertionV2 with Ed25519. A WebAuthn signature by itself is not a trusted display receipt.

## Version and extension rule

All listed fields are required, including option containers. Unknown fields, extra array elements, unsupported type, wrong revision or registry mismatch reject before authority evaluation. V2.1 deliberately has **no opaque critical-field bitmap or unsigned extension bag**. A new field/enum requires a new exact schema revision with golden vectors and authenticated reader negotiation. Readers must explicitly advertise each supported `(type,revision,registry_digest)`; intersect with policy minimum before session creation, pin in session/capability digest, never change during an attempt. No silent N/N-1 semantic downgrade. Old names without a complete schema are documentation aliases only, not accepted wire alternatives.

## Payload references and retention

A digest reference means exact canonical bytes of the named registered type, unless explicitly raw content (patch/blob/output). The type/producer/retention mapping is in CONTRACT_AUTHORITY.md and the record's semantic rules. Resolve within tenant custody, enforce byte/size/expiry, verify hash before use, reject missing/expired references. Configurations and tool JSON schemas belong to explicitly pinned analyzer/provider profiles; unknown profile/schema or unvalidated semantic configuration is UNSUPPORTED, never PASS. Audit envelopes contain metadata only; protected source-bearing custody is separate and erasable. Recovery-intent metadata is retained until all effects are resolved under the journal contract.

## Standards references

The constrained encoding above specializes [RFC 8949 deterministic CBOR](https://www.rfc-editor.org/rfc/rfc8949.html); authority signatures use [RFC 8032 Ed25519](https://www.rfc-editor.org/rfc/rfc8032.html). These standards specify the primitives, not the proposed Mastercoder implementation.

## Registry identity

`registry_digest` is plain SHA-256 of the exact distributed REGISTRY.json UTF-8 file bytes, including whitespace and final LF. It is not the digest of a reserialized JSON object. Any byte change requires a different negotiated registry identity and renewed applicable evidence. AtomicPrototypeClaimV1 is a JSON document specification, not a CBOR runtime record; its standalone JSON Schema defines its fields.
