# External Effect Exactness and Recovery

## Decision and scope

V2.1 selects a synchronously witnessed external-effect intent journal in a separate restore domain. PostgreSQL remains business authority; the journal supplies durable knowledge of every possible provider send even when an RPO restore loses its database row. Ordinary asynchronous audit export is insufficient. This bounded addition is required by findings 9–11; it is not a general queue replacement.

Every mutating provider call, billable model request, check create/update, dependency credential-bearing acquisition and Git publication call uses this protocol. Read-only reconciliation calls have audited attempt identity/rate limits; they cannot mutate state or consume a new publication authorization. PublicationOperation groups EffectIntentV2 children, such as each CREATE_BLOB, CREATE_TREE, CREATE_COMMIT, CREATE_REF and CREATE_FIX_PR. CREATE_CHECK, UPDATE_CHECK and model requests are separately typed effects. The parent is never itself a send grant.

## Immutable request and state records

EffectIntentV2 is immutable: effect_id; logical_operation_id; parent_operation_id; predecessor_effect_ids; call_attempt; effect kind; tenant/repository/account/provider and repository/authority epochs; canonical request digest; exact authorization proof digest; creation and dispatch/request deadlines; optional provider idempotency token; initial PENDING state. The schema is authoritative for field order and wire types. EffectStateV1 is an append-only signed state revision referencing the stable intent digest, prior revision, state, STARTED/result times, provider observation and reconciliation evidence. Neither changing state nor importing a lost row changes the original request digest.

Each child call binds its own HTTP method, normalized provider operation/path and exact body/object digest. Token values are never journaled. Request material needed for reconciliation lives in custody with its digest and permitted retention; source-bearing Git payloads remain encrypted under tenant custody. Journal metadata alone must enumerate and identify all possible effects without relying on lost PostgreSQL rows. Missing body custody never authorizes reconstruction from an untrusted alternative.

## Journal durability and writer topology

A designated sequencer appends a hash-chained record to two durable copies in independent storage/recovery domains, at least one outside the control database region/restore boundary. Both copies must confirm fsync of the same sequence, previous digest, record digest and current journal epoch before the witness receipts are returned. The sequencer serializes append order and uniqueness; the witness rejects chain gaps, conflicting effect claims or an old fenced epoch. Each side signs its receipt with a different custody key. Only configured journal/gateway workloads can append; an ordinary API cannot mint a witness receipt.

No automatic failover that loses a required copy is allowed. Recovery selects a single sequencer only with old writer/egress fencing evidence and both copies' authenticated committed high-water marks. A partition cannot produce two accepted chains; absent agreement, stop sends. Journal copy health, durable-storage behavior and independent failure domains are capability prerequisites tested under atomic P0-08/P0-10. The declared failure envelope tolerates loss/rollback of the business PostgreSQL plane and one journal failure domain while retaining a complete authenticated copy. Simultaneous destruction/compromise of every journal copy is outside that envelope and requires publication freeze; do not claim unconditional zero loss.

## Dispatch protocol and crash matrix

1. PostgreSQL creates PENDING intent with immutable request/auth references, logical-key uniqueness, audit and outbox. The gateway validates request structure/capability membership but has not sent anything.
2. Append PREPARED with the complete canonical EffectIntentV2 bytes, required authorization/custody metadata, and request-custody reference to both journal copies. Each referenced metadata record needed to enumerate/reconstruct intent is itself durably attached in the witness domain before acknowledgment; digest-only pointers into the restorable database do not qualify. Confirm both witness signatures. Missing/lost acknowledgment: DO NOT SEND; reread by exact digest for bookkeeping, without acquiring send authority.
3. In a PostgreSQL transaction, lock current authority and effect; revalidate current approval/capability, tenant/repository epochs, signer/credential generations, exact plan/request/custody, predecessors, unexpired lease where required, deadlines and parent state. CAS PENDING→STARTED, consume the individual authorization and append audit. The committed start certificate binds the immutable intent and deadline. Database failure/unknown commit outcome means DO NOT SEND until exact committed status is established and the original dispatch window still permits it.
4. Append SEND_ARMED referencing that committed certificate. The sequencer grants exactly one claim for (effect_id, intent_digest) and binds it to the active dispatcher session. Both durable receipts are required. Only the requesting live dispatcher may use the receipt once; recovery/replay never obtains a replacement send claim. A lost acknowledgment or dispatcher crash is conservatively UNKNOWN, even if no packet actually left.
5. The live gateway starts exactly one provider call before dispatch_deadline, using the prevalidated method/path/body and provider token in its isolated credential boundary. SDK automatic retries/redirects are disabled for mutations unless separately modeled and proven safe. A redirect is not a new allowed endpoint. Client request activity is bounded by request_deadline. Persist OBSERVED response/result in the journal before projecting its outcome into PostgreSQL; failure to persist leaves UNKNOWN.
6. Reconciliation appends evidence and terminal snapshots. Every additional actual mutation call is a fresh effect_id/call_attempt with fresh current authority; this includes a provider-guaranteed idempotent retry. It still belongs to the same logical effect and carries the same provider token/request digest when that guarantee requires it.

| Crash boundary | Recovery meaning |
|---|---|
| Before PREPARED | No send allowed; surviving PENDING may be rebuilt/revalidated |
| PREPARED but no STARTED/SEND_ARMED | No send allowed; after fencing all old dispatchers and checking full journal, terminal non-dispatch can be established |
| STARTED but no SEND_ARMED | No send allowed; use journal completeness plus sender fencing, not PostgreSQL absence alone |
| SEND_ARMED, before/after unknown send | Possibly sent; UNKNOWN, never replay the claim |
| Provider result observed but DB write lost | Import durable OBSERVED record, validate provider identity, project exact result idempotently |
| Business DB restore loses whole operation | Enumerate witness journal high-water range, reconstruct missing intent/tombstone and reconcile; scanning surviving DB rows is insufficient |

Default dispatch_deadline is no later than STARTED +5 seconds; request_deadline no later than STARTED +60 seconds, constrained further by the authority grant. Already-started calls have bounded client lifetime but may complete at the provider later. This residual interval is explicit. Revocation after CREATE_COMMIT but before CREATE_REF leaves an orphaned commit at most; the ref and PR calls fail their own pre-STARTED authority checks.

## Outcomes and replacement proof

PENDING → STARTED → CONFIRMED | FAILED_TERMINAL | UNKNOWN. UNKNOWN may enter MANUAL_RECONCILIATION; no state resurrects a sent effect. CONFIRMED requires the exact stable provider/account/repository identity and the expected request result (for Git, exact object/tree/ref/PR lineage); a similar-looking object or successful HTTP status alone is insufficient when result identity is missing. FAILED_TERMINAL records an actual terminal outcome and whether execution occurred, not merely a timeout or generic exception.

ABSENT_CONFIRMED is removed. A replacement may proceed only if either (a) evidence proves the original request never entered the send boundary and every old sender is fenced, using complete witness history; (b) the provider supplies a request-correlated terminal rejection/cancellation that guarantees no execution now or later; or (c) a documented provider idempotency guarantee covers the exact operation/token/body/account and the retry is within its retention interval. The reconciler records the proof kind, source identity, observations, guarantee version, expiry and independent reviewer where manual. It then revalidates fresh authority and creates a new attempt. A not-found read, elapsed local timeout, expired lease/token, missing webhook or absent database row is never enough.

For GitHub operations without a proven suitable idempotency/terminal-nonexecution contract, no such retry capability is claimed. Read exact Git object identity, exact destination ref and resulting commit, or PR identity plus source/base/plan digest. Ref not found can later become present; a missing PR search result may reflect delay or indexing. Preserve UNKNOWN/MANUAL_RECONCILIATION indefinitely until exact outcome is known. Immutable object creation may have naturally repeatable object identity, but do not generalize that to ref/PR/check creation or claim a successful second response proves the first request absent. P0 provider tests must establish operation-specific rules before enabling replacements.

## Restore, revocation and retention

Every provider sender is fenced before restore promotion. The recovery authority compares both journal copies and authenticates the last committed high-water mark, loads every intent/SEND_ARMED/observation after the restore checkpoint and all still-open earlier effects, and imports missing identities under original epochs as historical recovery facts. It never interprets recovered authorization as current. Unknown effects remain blocked; costs settle even after epoch fencing. A monotonic journal JournalEpochFenceV1 and restored security authority prevent old epoch/generation/nonce resurrection.

Keep each journal intent, send claim, result/tombstone and custody reference through terminal reconciliation and at least the longest PostgreSQL backup/restore horizon plus the provider idempotency/discoverability retention horizon. Unresolved effects have no automatic purge; source bytes follow disclosed tenant custody policy, and expiration prevents further publication while metadata/tombstones persist. After all open uncertainty is resolved and safe checkpoints exceed retained backup horizons, compact with a signed checkpoint preserving logical-key deduplication and every unresolved identity. Customer-requested deletion cannot silently remove the only uncertainty tombstone; metadata retention and unavailable-byte status are disclosed in document 24.

## Validation obligations

Atomic claims must cover acknowledgment loss at every boundary; duplicate outbox/dispatcher; two journal partitions; old-session sends after failover; database restore before intent creation; lost result persistence; provider late completion after a not-found read; revocation between commit and ref; duplicate check writes; witness copy loss; and retention/compaction while an effect is unresolved. The required observation is zero unjournaled sends, zero unauthorized later child effects, no automatic retry after unknown, and complete recovery enumeration. All remain NOT_RUN in this architecture task.

For checkout/dependency egress, each actual HTTP call uses AcquisitionRequestV1 with exact broker-derived origin/method/target/body and selected OID/package, bounded response size and grant_digest. EffectIntentV2.canonical_request_digest hashes this per-call request, not the aggregate grant. Authorization proof still references the finite grant. No credential value is included in persisted request bytes.
